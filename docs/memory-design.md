# Дизайн памяти, личности и напоминаний Operator

Проектный документ. Синтез четырёх изученных систем поверх решений single-voice
архитектуры (25.08.2026): пользователь разговаривает только с оркестратором;
треды, календарь и напоминания — его собеседники, а не собеседники пользователя;
ничего из тредов не показывается as-is; каждое сообщение пользователя вытесняет
идущий ход оркестратора.

Ревизия 2.1 (25.08.2026): после двух независимых ревью (критик + верификатор
против первоисточников) и финального контрольного ревью снапшот-логики. Ключевые изменения: снапшот-модель
push вместо «в каждый конверт», слияние reminders в automations, схема now_items
с source/thread_ref, owner.timezone, rollup из journal_entries, oneShot-рантайм
фоновых прогонов, автодистилляция и судьба maintainStructuredMemory,
пример-рендеры слоёв.

Статус: дизайн, до реализации. Дополняет `dialogue-flow.md` (карта текущего
поведения) и `audit-2026-08-24.md` (баги). Ссылки на строки кода — на дерево от
25.08.2026; якорь — имя константы/функции.

## 1. Главный принцип: push карту, pull территорию — снапшотами

Pull-поиск решает только «известные неизвестные»: он срабатывает по триггеру в
сообщении. Имплицитную релевантность (тон, стоящие ограничения, «кто такой
Даня», сам факт существования знания) он не решает — модель не ищет то, о чём
не подозревает. Эмпирика: в smartex работают ровно always-loaded слои, а
pull-слой `memory/` атрофировался до полного отсутствия; эффект «всегда в
курсе» у blick — целиком push; grok-bot пушит ядро памяти снапшотом на эпоху
компакции.

**Критичная поправка ревизии 2: у нас персистентная сессия, а не свежая сессия
на задачу.** NOW-передача смены в smartex работает потому, что каждая задача —
новая сессия, читающая NOW первым действием. Наш оператор — одна резюмируемая
сессия: конверт каждого хода становится новыми токенами в её истории. Пушить
полный слой каждым конвертом — значит копить N копий по ~6 КБ (~1.5–3 K токенов
кириллицы), за 50–70 ходов ~100 K токенов дубликатов, ускоренное достижение
порога компакции 80 % и частые многоминутные «обслуживания памяти». Межходовой
prompt-cache этого не компенсирует: кэшируется префикс истории, а не
повторяющийся паттерн внутри новых ходов.

Поэтому **снапшот-модель** (как у grok-bot, эпоха = компакция):

- **Полный push** — ровно в четырёх случаях: (а) первый ход новой/восстановленной
  сессии, (б) первый ход после компакции (восстановительный промпт и есть этот
  снапшот), (в) первый ход после паузы класса `significant`/`cold-resume`
  (§2.7) — если с последнего полного push успело что-то измениться,
  (г) **fresh-session-replay**: ветка `askOperator`, пересоздающая сессию по
  `/session|resume|not found/` и реплеящая промпт, обязана пересобрать его как
  полный снапшот — реплей дифф-хода в свежую сессию оставил бы оператора без
  now и индекса до следующей компакции.
- **Внутри эпизода** (`light`-паузы) — только дифф now-state (обычно пуст →
  секция отсутствует) и синтетические сообщения.
- **Baseline диффа персистентен.** В `runtime_state` хранится (session id,
  эпоха снапшота, hash отрендеренного now-слоя последнего успешно
  **отправленного** промпта). Baseline двигается в момент отправки (вытеснение
  после отправки не откатывает — контент уже в истории сессии); ошибка
  провайдера до принятия хода baseline не двигает; несовпадение session id
  (пересоздание, рестарт) → форс полного снапшота. Без этого демон после
  крэша не знает, что уже запушено.
- **Персона** — всегда в `--system-prompt`, в конверт не входит. У нас
  автозагрузки CLAUDE.md нет и не будет: `--setting-sources ""` намеренный
  (privilege-изоляция). Урок smartex — вся их система висела на одной точке
  отказа, автозагрузке конституции; сборка кодом демона устраняет этот класс.

Экономика после поправки: полный снапшот случается единицы раз в день
(компакции + холодные возвраты), а не каждый ход. Риск вымывания слоя в
длинном эпизоде закрывается диффом now-state и правилом персоны «на сомнении о
текущем состоянии — прочитай now заново» (`now.get` в pull).

## 2. Слои и носитель

Носитель — существующий SQLite. Markdown — только рендеры таблиц: файл без
схемы не сопротивляется распуханию (NOW.md smartex: дизайн «экран текста»,
факт 45 КБ, закрытые пункты месячной давности, дописывание абзацев в ту же
строку). Все бюджеты ниже — в **символах** (не байтах; для кириллицы в UTF-8
разница двукратная).

```
PUSH-СНАПШОТ (собирает демон, §1)
├─ now-state          — рендер now_items, ≤3000 символов
├─ индекс памяти      — рендер operator_notes (триггер → ключ), ≤3000 символов
└─ не-переоткрывать   — рендер description'ов категории anti-rediscovery, ≤1000
ДИФФ ВНУТРИ ЭПИЗОДА
└─ изменившиеся now-пункты с прошлого хода (обычно пусто)

PULL (инструменты)
├─ memory.search      — FTS + вектора по заметкам и тредам (есть)
├─ memory.get         — заметка по ключу (новый)
├─ now.get            — полный now-state по запросу (новый)
├─ memory.journal     — daemon_events за интервал + журнал и rollup'ы,
│                      когда интервал старше retention событий (расширен)
├─ journal.note       — запись в журнал по скелету §2.4 (новый)
├─ journal.read       — записи за день/интервал и месячные rollup'ы (новый)
└─ t3.thread_summary  — эпизодическая память треда (есть)
```

### 2.1 Персона

Расцепить: `persona.md` (голос, тон, границы — **нумерованные правила**;
номер — стабильный идентификатор, по которому агент обосновывает и действие, и
бездействие; нумерацию не сдвигать, только дописывать) отдельно от `policy.md`
(полномочия, риски) и env (из инструментов).

Обязательные правила персоны, вытекающие из ревью:

- «Утверждение о факте — от кого угодно — проверяется до записи; `verified_at`
  ставится только после проверки инструментом или явного подтверждения
  владельца» (дисциплина blick, поведение для колонки §2.3).
- Протокол самокоррекции роутинга (server-kit): «"ты же знал про X" → найди
  заметку, пойми, почему триггер не сработал, почини description-триггер — не
  извиняйся текстом».
- «На сомнении о текущем состоянии — `now.get`, не память эпизода».

Two-layer reliability: правило, которое не должно молча сломаться, живёт в
промпте И в коде (формат Telegram, даты/зоны, «никогда as-is из тредов»,
redaction). Компакция: восстановительный промпт обеих веток (Claude `/compact`
и Codex re-seed) включает сжатую выжимку нумерованных правил + полный
push-снапшот — это «первый ход эпохи» по §1.

Обновление персоны — только диффом через ретро (§5), автоправки нет.

### 2.2 Now-state

```sql
CREATE TABLE now_items (
  id          TEXT PRIMARY KEY,
  owner_id    TEXT NOT NULL,
  section     TEXT NOT NULL,      -- 'active' | 'blocked' | 'waiting' | 'next' | 'debt'
  content     TEXT NOT NULL,      -- ≤200 символов (энфорс кодом)
  source      TEXT NOT NULL,      -- 'agent' | 'daemon'
  thread_ref  TEXT,               -- id T3-треда, если пункт про тред
  origin_job  TEXT,               -- ingress-job id хода-создателя (идемпотентность реплея)
  status      TEXT NOT NULL DEFAULT 'open',   -- open | half | closed
  journal_ref TEXT,               -- слаг журнальной записи (имя, не id)
  valid_until TEXT,               -- TTL
  updated_at  TEXT NOT NULL
);
```

Реализация (пакет 2.2) добавила две колонки сверх этого списка, обе — прямые
следствия правил ниже: `create_seq INTEGER` (вторая половина ключа
идемпотентности реплея; уникальность — частичный индекс по
`(owner_id, origin_job, create_seq)`) и `created_at TEXT NOT NULL` (фокус
ранжируется по времени СОЗДАНИЯ пункта, чего ни одна перечисленная колонка не
выражает).

Правила (энфорс кодом):

- **Двойная бухгалтерия.** Демон сам ведёт пункты о тредах: старт треда →
  insert (`source='daemon'`, `thread_ref`), терминал → close. Гранулярность —
  **пункт на тред** (батч из 5 форвардов, породивший 1 тред = 1 пункт). Агент
  ведёт всё остальное через `now.update` и **может менять `section`/`status`
  демоновских пунктов** («перенеси в blocked»), но не `content` — контент
  демоновского пункта регенерируется демоном.
- **Идемпотентность реплея.** `now.update` при create проставляет `origin_job`
  = ingress-job текущего хода; ключ идемпотентности —
  `(origin_job, порядковый номер create внутри хода)` (не секция: один ход
  легитимно создаёт два пункта в одной секции, а частичный реплей должен
  доподнять недостающие, не слить их). Повтор ключа — upsert. Аналог уже
  решённого `job_thread:<ingressJobId>` для тредов.
- **Бюджет — свойство рендера, не записи.** При записи энфорсится только
  per-item (`content` ≤200, без код-блоков). Рендер укладывается в 3000
  символов ранжированием: демоновские active/blocked всегда, дальше по
  `updated_at`; не вошедшее — строкой `(+K пунктов — now.get)`. Отказов записи
  из-за агрегата нет: отказ посреди хода = лишние итерации при ждущем
  пользователе, а вытеснение хода может убить запись совсем.
- **Закрытое** уходит из рендера немедленно; при закрытии автоматически
  создаётся журнальная запись (архив). **Просроченный TTL** скрывается из
  рендера сразу, перенос в журнал делает секретарь.
- **`half`** — семантика blick `[~]`: «сделано наполовину, остаток заведён»,
  остаток формулируется в content.

Судьба фокуса: из UX фокус убран (single-voice), но **машинная привязка
остаётся** — `focus_state` (per-owner, как сейчас) продолжает жить как
внутренний указатель primary-треда для `relatedThreadIds` исходящих и
восстановления; он становится производным от демоновских `active`-пунктов:
последний по **времени создания пункта** (старта треда, не `updated_at` —
регенерация content демоном не должна двигать фокус), пункты, перенесённые в
`blocked`, из кандидатов исключаются. `memory.update_focus` упраздняется;
команды `/focus`, `/stop`, `/cancel` удаляются. **Детерминированный аварийный
люк сохраняется**: голое cancel-слово («стоп»/«отмена»…) продолжает работать
обоими путями dialogue-flow §4 — preemption рантайма (путь A) и
interruptThread по reply/фокусу (путь B) — потому что остановка не имеет права
зависеть от успешного LLM-хода (rate-limit или лежащий провайдер не должны
лишать владельца стопа). Умирают только slash-команды; смысловая остановка
(«останови сборку») — задача агента через `t3.interrupt_thread` (реальное имя
тула).

**Пример рендера** (язык заголовков — английский, как весь конверт; контент —
как записан):

```
Current state (owner's work):
ACTIVE
- [T3 refactor-api] Рефакторинг API: воркер пишет тесты (thread t_9f2, обновлено 14:02)
BLOCKED
- Деплой staging ждёт токен от Дани [~ остаток: прогнать миграции] → journal 2026-08-25-staging
NEXT
- Ответить бухгалтеру про НДС до четверга (до 2026-08-28)
(+3 items — call now.get for the full list)
```

Пустой слой рендерится явной строкой (`No current work items.`) — структура
конверта не плавает, стиль существующих «No attachments.» сохранён.

### 2.3 Память фактов (operator_notes, расширение)

```sql
ALTER TABLE operator_notes ADD COLUMN key TEXT;            -- слаг для update-in-place
ALTER TABLE operator_notes ADD COLUMN description TEXT;    -- строка индекса: ТРИГГЕР → суть
ALTER TABLE operator_notes ADD COLUMN verified_at TEXT;
ALTER TABLE operator_notes ADD COLUMN valid_until TEXT;
ALTER TABLE operator_notes ADD COLUMN superseded_by TEXT;
CREATE UNIQUE INDEX operator_notes_key ON operator_notes(key)
  WHERE key IS NOT NULL AND status='active';
```

- **Description — это триггер, не аннотация.** Форма «когда/при X → суть»
  («отчёты для Дани → формат и канал», «закупки дронов → см. цены»), ≤120
  символов, энфорс в тулзе с фидбек-текстом: `Description = routing trigger
  ("when X → what"), not a summary. Content lives in the note.` Индексная
  строка отвечает на вопрос «когда мне это читать» — иначе карта не
  маршрутизирует (урок server-kit).
- **Update-in-place по ключу**: remember с существующим key — в одной
  транзакции: старая версия → `status='superseded'` + `superseded_by`, из FTS
  и **из векторной таблицы** удаляется (иначе повторится известный баг
  expireOperatorNotes: осиротевшие вектора будут ложно триггерить дедуп);
  новая — insert + индексация. Все существующие фильтры чтения
  (`listNotes`, FTS-join, векторный join) ревизуются на `status='active'`.
- **Самоопровержение с датой**: персона предписывает при перезаписи факта
  фиксировать «перемерено ДД.ММ, было неверно, потому что …» в теле новой
  версии — агент запоминает тип своей ошибки, не только факт.
- **valid_until**: просроченный факт в выдаче поиска и в `memory.get`
  помечается `[not verified since <date> — treat as hypothesis]`; секретарь
  раз в месяц собирает просроченные в один вопрос владельцу.
- **Индекс-карта в push**: только `description → key` активных заметок,
  ранжирование recency+usage, бюджет 3000 символов, хвост —
  `(+K notes — memory.search)`. Полные тела — pull. **Anti-rediscovery — не
  исключение**: в push идут только description'ы этой категории (отдельным
  блоком, 1000 символов), тела — через `memory.get`. Противоречие ревизии 1
  («не пушим контент» vs пуш тел) снято.
- **Категории**: `anti-rediscovery` (установленное + негативное знание
  «пробовали — не работает»), `decision` (ключ `decision-NNN-slug`, тело
  «контекст → решение → цена»), `incident` (симптом → root cause → как чинили
  → уроки; читается при похожих симптомах — жанр постмортема, а не факта),
  прочие доменные.
- **Redaction — по точкам вывода, с перечнем.** Хранение: маскирование с
  сохранением префикса и длины (`ghp_a1…[52]`) вместо уничтожения — ссылочность
  сохраняется, необратимой порчи нет; настоящие секреты ловятся
  энтропия+контекст в тулзе записи. Полная редакция — на каждом выводе наружу,
  перечень закрываемых точек: push-рендеры конверта, результаты
  `memory.get/search/journal`, journal.read, тексты в Telegram, dashboard
  `/api/state`, и **`daemon_events.payload_json` при записи** (сегодня пишется
  без редакции — закрыть). Легаси-заметки, уже искалеченные старой редакцией,
  помечаются поиском `[REDACTED` → категория `legacy-redacted` (verified_at
  недостаточно — после ALTER он NULL у всех).

### 2.4 Журнал

Три слоя (формула smartex «слой 1 гарантирует, слой 2 воспитывает, слой 3
подчищает»); наши слои 2–3 сильнее оригинала, потому что демон видит каждый
ход с точным id, а не «окно 2 часа по времени» (их stop-hook на этом дважды
погорел: ложные срабатывания каждую сессию + пропуск при любом сегодняшнем
файле).

1. **Action_log = `daemon_events`** — есть. **Предусловие пакета журнала, не
   пожелание**: дописывать усечённые аргументы (≤500) и результат/ошибку
   (≤300) мутирующих вызовов + привязку к ходу (`opturn`) — по `{tool,
   durationMs}` секретарь нарратив не восстановит в принципе.
2. **Проверка в моменте.** После хода с мутациями демон проверяет: была ли
   запись агента (`source='agent'`) в now/журнал. Не была — строка-напоминание
   в следующий конверт, но: (а) только внутри эпизода (`light`-пауза) и не
   после вытеснения хода — несвежее напоминание хуже отсутствующего; до
   пакета 3 проверяется только now-запись (тулз журнала ещё нет);
   (б) максимум 2 напоминания подряд, дальше — задача секретарю (анти-луп,
   аналог `stop_hook_active`); (в) флаг «ход имел мутации» — в
   `runtime_state`, переживает рестарт. Вытесняемость ходов делает секретаря
   **основным** механизмом консистентности, проверку в моменте —
   воспитательным.
3. **Ночной секретарь** — деталь в §5.

**`journal_entries (slug PRIMARY KEY, day, body, source: agent|scribe|daemon,
kind, thread_ref, origin_job, create_seq, created_at)`** — нарратив; скелет
«Сделано / Решения / Найдено попутно / Следующий шаг». Автозаписи демона
(закрытие now-пунктов) — `source='daemon'`; `(origin_job, create_seq)` хранит
идемпотентную личность записи агентского хода.

**Ротация:** `daemon_events` — 30 дней как сейчас. `journal_entries` — вечно.
Месячный **rollup строится из journal_entries** (они вечные — арифметика
«rollup до pruning» из ревизии 1 не сходилась: сводке за месяц нужны события
возрастом до 60 дней, retention 30; зависимость от daemon_events убрана).
Устоявшееся из rollup'а секретарь предлагает перенести в `anti-rediscovery`.

### 2.5 Автодистилляция (восстановлено из §0 — в ревизии 1 отсутствовала)

Канал наполнения памяти без «запомни»: владелец упоминает факты мимоходом
(«не пиши мне по утрам», «Даня теперь отвечает за склад»), правило 9 smartex.

- Ночью секретарь прогоняет **дельту переписки** (входящие+исходящие из
  SQLite с последнего прогона, состояние — `runtime_state`) через oneShot с
  промптом дистиллятора server-kit («ONLY new, durable, long-lived facts…
  If nothing — reply NOTHING»).
- Результат — заметки `source='distilled'` с предложенным key/description,
  `verified_at=NULL` (не подтверждено!). Автомат **не пишет** в курируемые
  ключи: коллизия с существующим key → предложение merge в утреннем дайджесте
  секретаря, не перезапись.
- Дедуп — машинный на записи (§2.6), не промптовый: «NOT already in memory»
  с обрезкой контекста не масштабируется.
- Анти-луп: дистиллятор не читает свои заметки как вход, только переписку.
- **Судьба `maintainStructuredMemory`**: упраздняется как отдельный механизм;
  его роль (извлечение перед компакцией) переходит дистиллятору секретаря +
  компакт-снапшоту. Переходно, если остаётся — обязан писать по новой схеме
  (key/description), иначе плодит неиндексируемое легаси мимо карты.

### 2.6 Ретрив

FTS5 + гибридный скоринг остаются. Замена `localMemoryVector` (хеш-триграммы
128d) на локальную ONNX `paraphrase-multilingual-MiniLM-L12-v2` (384d) — с
фолбэком на хеш при недоступности рантайма; пересчёт векторов только при смене
модели или изменении заметки (заодно уходит O(notes)-переэмбеддинг каждого
бута). **Дедуп на письме включается только после MiniLM** — пороги 0.85
(merge-предложение) / 0.7 (cross-link) сняты с MiniLM-пространства и на
хеш-векторах бессмысленны (у текущего скоринга рабочий порог 0.18). До MiniLM
дедуп — только точное совпадение key.

### 2.7 Классификатор пауз и таймзона

**Новое поле конфига `owner.timezone` (IANA) — предпосылка половины дизайна**:
окно секретаря «02:00–04:00 локального времени», human-даты («завтра в 9:00»),
кросс-суточная классификация пауз, граница суток 03:00 для «вчера». Сегодня в
конфиге зоны нет вообще (есть только внутри daily-расписаний automations).

Классификатор (по owner.timezone; демон хранит момент последнего сообщения
владельца в `runtime_state`) — явный маппинг:

| Пауза | Класс | Gap-строка | Push |
|---|---|---|---|
| < 45 мин | тот же эпизод | нет | дифф |
| 45 мин – 2 ч | `light` | нет | дифф |
| 2 ч – 12 ч | `significant` | да | полный снапшот (если что-то менялось) |
| > 12 ч или смена суток (граница 03:00) | `cold-resume` | да | полный снапшот |

**Строки упорядочены**: первая подходящая по длительности выигрывает, и клауза
«смена суток» уточняет строки от 2 ч, а не перебивает все. Иначе сообщение в
02:55 и следующее в 03:05 пересекали бы границу и получали холодный снапшот —
именно на том классе пауз, про который граница ничего не утверждает. Реализация
(`packages/policy/src/pauses.ts`) читает таблицу так же; тест на обе стороны
границы — в `tests/memory-push.test.ts`.

Классификатор меряет молчание **владельца**: синтетические ходы (автоматизации)
и дайджест-ходы тредов не двигают `owner_last_message_at`, не получают
gap-строку и не тратят снапшот паузы. «Менялось ли что-то» за время отсутствия
считается от того, что владелец **видел последним** (`ownerSnapshotHash`
baseline'а) — фоновые дифф-пуши за время его отсутствия двигают общий baseline,
но не его.

Плюс правило персоны на `significant`/`cold-resume`: «сверься с now, не
продолжай эпизод как непрерванный». Оценка стоимости: significant с 2 ч даёт
реалистично 3–5 полных снапшотов в день (~10–17 K токенов) — приемлемо при
суточной компакции.

## 3. Напоминания, календарь, дневник («три аппы»)

Все три — собеседники оркестратора: срабатывание = синтетическое системное
сообщение в его конверт («system message from calendar: …»), оркестратор
пересказывает владельцу своими словами. Механика синтетического ingress есть
(automation-fire).

**Reminders — НЕ отдельная таблица** (ревизия 2; ревизия 1 дублировала
машинерию). У automations уже есть once/interval/daily с зонами,
идемпотентность `automation_runs UNIQUE(id, scheduled_for)`, backoff и
pause-after-5. Расширяем их:

- `automations.kind` = `'automation' | 'reminder'`; reminder — лёгкий fire
  («в момент X скажи владельцу про Y»), полноценный ход оркестратора, но с
  коротким промптом-контекстом.
- `automations.rrule` — опционально, для повторов сложнее interval/daily;
  DST-пересчёт по зоне записи.
- **`automation.update`** — тулза и для automations, и для reminders; закрывает
  известную болячку «перенеси на 10:00 = дубль». Delete — с подтверждением
  через существующий approval-механизм.
- **Эскалация игнорируемого fire** — по подтверждению, не по «есть входящие»
  (владелец, ответивший на другую тему, не гасит напоминание; молчащий ночью —
  не получает повтор впустую): fire с флагом `escalate` сразу создаёт
  now-пункт `waiting` (source='daemon', origin=automation); агент закрывает
  его, когда владелец по смыслу отреагировал; эскалация — один повтор короче
  по незакрытому пункту + отсутствию реакции, дальше пункт просто остаётся в
  now. `half`-семантика реминдеров не нужна — остаток живёт в now_items.
- Отображение владельцу: только человеческие даты в owner.timezone; ISO-UTC
  в чате запрещён two-layer-правилом (код рендера + персона).

Календарь: `calendar.*` (чтение/запись событий); напоминание о событии — это
reminder, созданный агентом при записи. Дневник: `journal.*` (§2.4) — записи
агента + чтение дней/rollups; редакция — секретарь.

## 4. Сборка конверта (итоговая)

Точка сборки — массив prompt в `answerDirect` (существующие «8 строк» —
было 9 до удаления фокус-строки пакетом 1.3 — становятся инструкцией хода). **Перечень точек `askOperator`, получающих
push-слой** (в ревизии 1 отсутствовал):

| Точка | Push |
|---|---|
| `answerDirect` (пользовательские + синтетические ходы) | снапшот/дифф по §1 |
| восстановление после компакции, смены провайдера | полный снапшот + выжимка правил (это первый ход эпохи) |
| fresh-session-replay внутри `askOperator` | пересборка промпта как полный снапшот (§1г) |
| нормализация worker-результатов, failure-recovery | **нет** (служебные one-shot задачи) |
| дистилляция/секретарь/библиотекарь | **нет** (свой промпт, oneShot) |

Структура полного снапшота: now-state → индекс памяти → не-переоткрывать →
`[gap: …]` → синтетика → инструкция хода → fenced-сообщение. Дифф-ход: только
изменившиеся now-пункты (или ничего) → синтетика → инструкция → сообщение.
Пустые слои — явные строки-заглушки. Рендеры живут в **policy-пакете** рядом с
`buildOperatorSystemPrompt` (данные — из storage, сборка — policy, вызов —
демон): тестируемость бюджетов юнитами без демона.

Компакт-снапшот (`buildOperatorMemorySnapshot`) переводится на те же рендеры —
единственный формат состояния, без параллельного.

## 5. Принуждение и гигиена

**Рантайм фоновых прогонов — только oneShot** (образец — `runMediation`:
«mediation must never occupy the main session»); главная сессия оператора —
никогда: иначе загрязнение контекста + ночные сообщения владельца в очереди за
секретарём. oneShot берётся из **Claude-ветки `SwitchableOperatorRuntime`
независимо от активного провайдера главной сессии** — постоянный Codex (у
которого one-shot канала нет) не должен молча убивать секретаря, «основной
механизм консистентности» §2.4.2. Если Claude-ветка недоступна тоже — прогон
пропускается с журнальной отметкой, догон следующей ночью, окно 48 ч; после
3 подряд пропусков — сообщение владельцу (гигиена не имеет права умирать
беззвучно).
Перед каждым LLM-проном — детерминированный `has_work()`-гейт (есть ли дельта
событий/переписки/просроченных TTL): тихая ночь не стоит ни токена.

| Механизм | Когда | Что делает |
|---|---|---|
| Линтер записи | в тулзе, синхронно | только per-item: content ≤200, description ≤120 и триггер-форма, без код-блоков; фидбек-тексты фиксированы в коде (структурный `{ok:false, hint}` — одинаково виден Claude и Codex) |
| Проверка в моменте | конец хода с мутациями | §2.4.2: напоминание в следующий конверт, внутри эпизода, ≤2 подряд, флаг в runtime_state |
| Ночной секретарь ✅ 3.1 | ежедневно, окно 02:00–04:00 owner.timezone, гейт `last_scribe_at` в maintenance | сверка daemon_events↔журнал↔реестр (дописывает с пометкой «восстановлено по event-логу»); TTL-переносы; ленивые description легаси-заметок; дневная сводка (с догоном пропущенных суток внутри 48-часового окна). Источник истины — event-лог и реестр, не воспоминания. **Дистилляция §2.5 — не здесь:** отложена в 3.2, где появляются `source='distilled'`, `verified_at` и машинный дедуп, без которых её результату негде лежать (см. §8.3) |
| Дедуп на письме | в memory.remember (после MiniLM) | §2.6 |
| Библиотекарь | еженедельно, oneShot | детерминированные чеки чинят сами (сироты индекса, битые journal_ref, superseded в FTS/векторах); LLM-находки → одно сообщение владельцу; правила формулировок: каждая находка — конкретное действие «что, где, как»; не уверен → WARNING, не CRITICAL; history находок NEW/KNOWN/RESOLVED + хронические |
| Месячный rollup | ежемесячно | из journal_entries (§2.4); устоявшееся → предложение в anti-rediscovery |
| Ретро персоны | еженедельно, oneShot | вход — **метрики, не ощущения** (smartex §8b, у них спроектировано и не запущено): % отклонённых approvals, % ложных алертов, просроченные now-пункты, случаи «знал, но не вспомнил» из журнала. Выход — дифф нумерованных правил persona.md на апрув владельцу. «Плохая метрика → правка правила, не "стараться лучше"» |
| Перепроверка фактов | ежемесячно | просроченные valid_until → один вопрос владельцу |

## 6. Миграция

1. Схема: ALTERы §2.3 (guarded-паттерн `migrate()` уже есть), `now_items`,
   `journal_entries`, `automations.kind/rrule/escalate` (существующие строки —
   `kind='automation'` по default), конфиг `owner.timezone`.
2. Транзакция supersede + ревизия всех фильтров чтения на `status='active'` +
   чистка FTS/векторов при supersede и expire (закрывает существующий баг
   осиротевших векторов).
3. Фокус: `focus_state` остаётся машинной привязкой, производной от
   демоновских now-пунктов; `memory.update_focus` и команды `/focus`, `/stop`,
   `/cancel` удаляются (single-voice); `relatedThreadIds` исходящих читает
   focus_state как раньше.
4. Легаси-заметки: `key=NULL` → в индекс временным форматом «первые ~100
   символов контента → id», ранжирование по updated_at, top-N; секретарь
   лениво дописывает description; `[REDACTED`-поиск → категория
   `legacy-redacted`.
5. Вектора: MiniLM-пересчёт активных заметок при первом старте после апгрейда;
   пересчёт впредь — только при изменении/смене модели.
6. `maintainStructuredMemory` — по §2.5.

## 7. Чего сознательно не делаем

- Markdown как первоисточник — только рендеры таблиц.
- Автоправка персоны — только дифф на апрув.
- Push контента заметок — только индекс (включая anti-rediscovery: тела — pull).
- Полный push каждым конвертом — только снапшоты по §1.
- Блокировка хода ради записи и write-time отказ по агрегатному бюджету.
- Отдельная таблица reminders — kind у automations.
- Отдельный векторный сервис — ONNX в процессе, фолбэк на хеш.
- Пермишен-гейт в двух местах (урок smartex: гейт и дырявый, и блокирует
  самопочинку) — полномочия только в policy-слое демона.

     а отсутствующие разделы получают `—`;
   - `memory.journal` для окна старше retention выбирает только вырезанную

     диапазон evidence и omissions. Тела из него, `journal.read` и ответа
